# Time tracking

How time entries work in the API: the running timer, manual entries, listing, editing and deleting. For backend developers and for anyone building a client against `/api/time-entries`. Describes the code as it is now.

## What this is

A time entry is one interval a user spent on a project, optionally with a description and tags. It is created either by the timer (`start` / `stop`) or manually with both ends known. Everything lives in `src/time-entries/`; the service orchestrates, and the rules sit in `time-entry.rules.ts`, `time-entry-tag-links.ts`, `time-entry-update.ts` and `time-entries.query.ts`.

Invariants:

- **Every entry the API creates has a project**, and the project must not be archived. Entries without a project come only from the Clockify import or from deleting their project (`ON DELETE SET NULL`).
- **Tags are project-scoped.** Every tag on an entry must belong to the entry's project; changing the project drops all current tags.
- **A user has at most one open entry** (`endedAt = null`) when entries are created through `start`. Starting a new timer closes the previous one in the same transaction.

## Surface

The full request/response contract is generated by Swagger at `GET /api/docs` (tag `time-entries`). Notes the schema does not express:

- Base path `/api/time-entries`. All routes require a JWT (Bearer). The user always comes from the token, never from the body.
- Validation runs with `whitelist` + `forbidNonWhitelisted`: unknown body fields return 400.
- All timestamps are ISO 8601 strings in UTC, in and out.

| Method | Path | Who | Returns |
| --- | --- | --- | --- |
| `POST` | `/start` | any user, for self | the new open entry |
| `POST` | `/stop` | any user, for self | the entry just closed |
| `GET` | `/current` | any user, for self | the open entry, or `null` |
| `POST` | `/` | any user, for self | the created manual entry |
| `GET` | `/` | self; admin/manager for anyone | `{ items, total, page, limit }` |
| `GET` | `/:id` | any authenticated user | the entry (no ownership check) |
| `PATCH` | `/:id` | owner only | the updated entry |
| `DELETE` | `/:id` | owner only | nothing |

Response fields worth knowing:

- `description` is always a string; an absent description is `""`.
- `project` is `null` when the entry has no project. It is also `null` when the project exists but its client could not be loaded; `projectId` is still set in that case.
- `tags` is always an array, possibly empty.
- There is no `duration` field; clients compute it from `startedAt` and `endedAt`.

## Rules and behavior

### Starting and stopping

| Call | Checks | Effect |
| --- | --- | --- |
| `start { projectId, description?, tagIds? }` | project exists and is not archived; tags belong to the project | In one transaction: closes the user's open entry at `now` (if any), creates a new entry with `startedAt = now`, `endedAt = null`, then links tags |
| `stop` | the user has an open entry, else 400 `No open time entry found` | sets `endedAt = now` |
| `current` | — | the user's open entry with project, client and tags, or `null` |

The entry closed by `start` is not checked against the 24 h limit or any other rule.

### Manual entries (`POST /`)

Checked in this order; the first failure wins:

1. `startedAt` inside the retroactive window (below) → else 400 `startedAt must be within the last 10 days and cannot be in the future`.
2. `endedAt > startedAt` → else 400 `endedAt must be greater than startedAt`.
3. `endedAt - startedAt ≤ 24 h` (exactly 24 h passes) → else 400 `Manual time entries cannot exceed 24 hours`.
4. `projectId` non-empty → else 400 `projectId is required`.
5. Project exists (404) and is not archived (400 `Project <id> is archived`).
6. Every tag belongs to the project → else 400 `Invalid tags for project: <ids>`.

**Retroactive window:** both `startedAt` and now are converted to America/Sao_Paulo wall-clock time and compared; `startedAt` must be between `now - 10 × 24 h` and `now`, inclusive. It is a rolling 240 hours, not "the last 10 calendar days".

### Listing (`GET /`)

| Query | Meaning |
| --- | --- |
| `userId` | Only that user's entries. A member passing someone else's id gets 403 `You can only list your own time entries`. |
| (no `userId`) | Members see only their own entries; admins and managers see everyone's. |
| `from`, `to` | Inclusive bounds on `startedAt` (not on `endedAt`). |
| `projectId` | Exact project. |
| `tagId` | Entries that have this tag. |
| `page`, `limit` | Defaults 1 and 50; `limit` max 200. |

Results are ordered by `startedAt` descending. `total` counts all matches, not the page.

### Editing (`PATCH /:id`)

Only fields present in the body change. The checks run against the values the entry will have after the edit:

1. The caller owns the entry → else 403. Admins and managers cannot edit other users' entries.
2. `projectId: null` → 400 `projectId is required`.
3. If `startedAt` is sent, it must be inside the retroactive window. An entry older than 10 days can still be edited as long as `startedAt` is not sent.
4. The resulting project exists and is not archived. **This runs on every edit**, even a description-only one.
5. `endedAt > startedAt` and the duration ≤ 24 h, also on every edit.
6. Tags:

| Body | Tags validated | Tag links after |
| --- | --- | --- |
| `projectId` changes, `tagIds` sent | `tagIds` against the new project | exactly `tagIds` |
| `projectId` changes, no `tagIds` | none | none (all removed) |
| same project, `tagIds` sent | `tagIds` | exactly `tagIds` |
| same project, no `tagIds` | the entry's current tags | unchanged |

`endedAt: null` reopens the entry. The entry fields and tag links are written in one transaction.

### Deleting

Owner only (403 otherwise); 404 if the entry does not exist. Tag links go with the entry.

## What this does NOT do

- No duration limit on timer entries. A timer left running for three days stops normally; only manual creation and edits enforce 24 h.
- `GET /:id` does not check ownership: any authenticated user can read any entry by id.
- No role can edit or delete someone else's entries, including admins.
- Reopening an entry with `endedAt: null` does not close the user's other open entry, so a user can end up with two open entries.
- The retroactive window does not apply to `start`/`stop`, and does not apply to `PATCH` unless `startedAt` is in the body.
- No overlap detection: entries of the same user may overlap.

## Gotchas

- Editing only the description returns 400 `Project … is archived` → the project check runs on every edit → unarchive the project first, or leave the entry as is.
- Editing only the description of a long timer entry returns 400 `Manual time entries cannot exceed 24 hours` → the 24 h check also runs on every edit, against the stored interval → shorten `endedAt` in the same request.
- Editing an imported entry fails with `Invalid tags for project` although no tags were sent → when the project does not change, the current tags are revalidated against it → send `tagIds` explicitly (possibly `[]`).
- Re-sending a `GET` response as the `PATCH` body returns 400 → `forbidNonWhitelisted` rejects fields like `id`, `project` and `tags` → send only `projectId`, `description`, `startedAt`, `endedAt` and `tagIds`.
- A spec passes but `pnpm typecheck` fails → ts-jest does not type-check; specs and `*.fixture.ts` are checked by `tsconfig.spec.json` → run `pnpm typecheck` before pushing.
